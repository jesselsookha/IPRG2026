Chapter 8 — Methods (Modularisation)

All the programs we’ve written so far in pseudocode have lived neatly between Start and Stop — one complete program from beginning to end. Now, in Chapter 8, we step into the world of Methods and Modularisation.

But before diving in, let’s look ahead to your future as programmers. When you land that first job, you won’t be building an entire program alone. You’ll be part of a team, each person responsible for smaller, well-defined tasks. These tasks are the methods — procedures and functions — that slot into the bigger system. Think of it like a puzzle: each piece is carefully crafted, and when combined, they form the complete picture. A method can be reused, called whenever it’s needed, and together they achieve the program’s goals.

Up to now, we’ve built full programs ourselves. Breaking them into methods will feel natural — and that’s exactly what this chapter will teach you. But in the professional world, you’ll often start by designing the pieces first, coding them, and then assembling them into the whole program. That’s the power of modularisation: building reliable parts that fit together seamlessly.

- Why Modular Programming?

Question - If your assignment was 20 lines long, did you need methods? 
Question - What about 2000? 5000 lines? 

Modular programming is how we survive complexity. 

*   Abstraction
- Simple explanation: I don't care how it works, I care what it does
- The idea that we have the ability to call/invoke a method whatever I am expected to get back from it, is what I am looking for. I am not immediately interested in what processing was executed to get to the result. 

- As programmers in the team, who are about to call these methods, we would expect the  programmer who coded the method, to have fully tested the method for all possible scenarios. 

- However, is this dangerous? If I am going to call a method to use in my part of the program, do I even have an understanding of the logic being implemented? Should programmers understand what's inside a method they didn't write? ** According to the above statement made, we expect the method to work as needed. So we don't really care of the exact code, but over time, we should take an interest. 

*   Reusability
- Coding a function or procedure once and using it multiple times 
- In real software companies, reused modules can save millions. 

Example:
- Payment processing modules reused in multiple apps.
- Login authentication reused across systems.

As students, copy-&-paste code is not resuability - that still means if something changes, students would need to copy-&-paste multiple times.  

*   Team collaboration
- Large systems are never built by one person 

Example: Student Management System
- One team: Login
- One team: Results processing
- One team: Reports

Without modularisation, everyone edits the same giant file which can lead to chaos.

- In a team, what if 2 programmers edit the same code? 
We should have something in place to prevent this from happening. 
We should have processes in place to help document all work being completed  

- If everything is clearly discussed, each person understands their responsibilities, we prevent conflict, hopefully...  

*   Maintainability
- Programs are written once, but maintained forever. 
- Remember that in the future, you would likely be joining a team that has an existing product, so your job is fixing or improving old code. Maintenance is important process we will all learn. 

Also, we don't have to wait for the future, next semester, when you are working on a project in a team for the WIL subject, each of the team members is going to come together, create the product, but also going to rework or revise certain areas after feedback and discussions, so maintenance.

- Types of Modules

* Control Module (Main Program)
- The Main program should read like a story 

	readMarks()		// input 
	processResults() 	// processing
	displayReport()		// output 

- This is not just the only variation 
- There are many more methods we can call 
- Will Main contain calculations? - We would prefer that it does not, because of what this chapter wants us to learn - but - if it happens, there must be a reason 

* Initialisation Modules
- Executed once at the start of the program 
- Set starting values - initialize variables, high, low, sum, count, and whatever else 
- Read initial input

* Processing Modules
* real work
- Calculate totals & averages 
- Find highest and lowest marks
- Making decisions 
- Sorting arrays 
- Search 
- Calculate percentages 

Each method (procedure, function) should do ONE thing. Yes there are times when we will execute a few things within these blocks of code, but that ONE thing means that it has a single purpose. 

	displayReport() - its main job is to display the report, but within, there might be a 	few extra things that are done. 


* Wrap-Up (Final Output) Modules
- Executed once at the end of the program 
- Display results 
- Print summaries 
- Close file and database connections

- Structure of Methods

0. methodName ([dataType parameter1, dataType parameter2]) [returns dataType]
1.	// code 
2. return [variable / value]

Now let's break it down: 

Method Header
*   Name	// good names reduce comments - helps identify before reading the code . 

*   Parameters  // optional - these are local variables declared as part of the header - because these variables are declared here, it means that when we call the function or procedure, we will need to pass values (known as arguments) so that these values can be used in the programming inside the block. 

*   Return type // only needed when the block is a function, because the function must return a value back to the "whomever" calls it. 

** Remember that both a procedure and a function use the same format but with key differences. 

Example: procedure (does not return a value)

0. readMarks() 
0. processMarks() 
0. displayStudent(string strName, string strStudentNum) 

Example: function (must return a value)

0. retDiscount() returns num 
0. returnDiscount(num fltPrice) returns num

Method Body
*   Logic statements
*   Local variables

Inside of the block, we are allowed to have a declarations statement that declare local variables - these variables are used in the processing of the block and will disappear after execution. 


Return Statement

return ends the method immediately. 
If its a procedure, the return statement is just the keyword: 
	return
If its a function, the return statement is the keyword with a variable or a value: 
	return true 
	return fltDiscount

* Exist only inside method.
* Cannot be accessed outside.
* Remember the example spoken about in class about our Android Studio Projects and the variable declarations inside of the Activity.

- Modularisation Process

*   Write main first
- Main = your blueprint 
- Write comments first to help identify 

Example 
0. Start 
1. Declarations 
	  ... 
2.	// get input 
3.	// calculate totals 
4.	// display output 

- Each of the comments can turn into a method call 

*   Identify responsibilities
- Each method should have: ONE responsibility.

*   Break large tasks into modules

*   Functional cohesion
- Everything inside method contributes to one purpose.


*************

0. Start 
1. Declarations 
	   num intAge 
	   num intTotal 
	   num fltAvg 
	   num intCount 

2.	intTotal = 0 
3.	intCount = 0 

4.	output "Enter age (-1 to Stop): " 
5.	input intAge 

6.	while intAge <> -1 
		  intTotal = intTotal + intAge 
		  intCount = intCount + 1 
		  output "Enter age (-1 to Stop): " 
		   input intAge
	endwhile 

7.	fltAvg = intTotal / intCount 
8.	output "The average age is " + fltAvg + " years." 
9. Stop
