-- Multiple if…then Statements

There are 3 variations that are shared: 
	* straight-through logic (separate if..then statements)
	* positive logic (nested if..then statements)
	* negative logic (nested if..then statements)
	

-- Straight-Through Logic

Separate independent if's

- Example

1. Declarations 
	num intMark

		output "Pass"

// Both if..then statements can run.

- Variations - The following was discussed with the intention of being able to see the mistakes. 
Since both of the above conditions is about the marks, the discussion was, could we combine the 2 if..then statements into 1 and use a compound condition


1 > using OR with a single alternative if..then statement 

	if intMark >= 50 OR intMark >= 75 then 
		output "Pass" 
		output "Distinction" 
	endif 

	if mark is 60 - Pass & Distinction - is this correct?  
	but if mark is 80 - what is the output? 

2 > using AND with a single alternative if..then statement 

	if intMark >= 50 AND intMark >= 75 then 
		output "Pass" 
		output "Distinction" 
	endif 

	if mark is 65 - it does not print anything - this is wrong 
	if mark is 80 - Pass and Distinction is outputted, that is correct 


3 > using OR with a dual alternative if..then..else statement 

	if intMark >= 50 OR intMark >= 75 then 
		output "Pass" 
	else 
		output "Distinction" 
	endif 

4 > using AND with a dual alternative if..then..else statement 

	if intMark >= 50 AND intMark >= 75 then 
		output "Distinction" 
	else 
		output "Pass" 
	endif 

Both 3 & 4 - seems to be correct, but when we executed the code, and noted some marks, it worked in some cases, but again, not for every possible mark. 

So it turned out that the 2 simple (single-alternative) if..then statements was the correct choice for this example. While both the conditions was about the marks, the results, "Passed" & "Distinction" was never related. 

So we follow the rules of straight-through logic.

An if..then inside an if..then

The Art of the Decision

In programming, a solution that "works" is only the beginning. As we have seen with these four variations of grading logic, the same result can be achieved through different lenses: 

Positive vs. Negative logic and Ascending vs. Descending ranges.

Why is it important to master all four? Because as a programmer, you aren't just a "writer"—you are an optimizer and a communicator.

1. Designing for the Data (The "Efficiency" Factor)

We often write code assuming all data is equal, but in the real world, it rarely is. 

- If you are grading a Master’s level course where 90% of students get an "A," starting your check at the top (Positive Logic, Descending) is the fastest path. 
- If you are screening for a remedial program where most students score below 50, starting at the bottom (Positive Logic, Ascending) saves the processor from checking five unnecessary conditions for every student.

The Lesson: Know your data. Choose the path that reaches the most common result the fastest.

2. Designing for Humans (The "Readability" Factor)

Code is read by humans far more often than it is written. 

- Positive Logic (If 'this' is true, do 'that') generally mirrors how humans think, making it easier to debug.
- Negative Logic (If 'not' this, then check 'that') can sometimes feel "inside out," but it is a powerful tool for filtering out exceptions or "edge cases" early.

The Lesson: If a teammate can’t understand your logic in ten seconds, the code is a liability, even if it works.

3. The Power of Choice

There is rarely "one right way" in software development. By learning these four variations, you are building a toolbox. 

- One method might be easier to maintain (e.g., adding a "D+" grade later).
- Another might be easier to test because the boundaries (< vs <=) are more distinct.


We don't learn four ways to do one thing just to be thorough. We learn them so that when we face a complex problem, we don't just grab the first tool we see. We look at the requirements, look at our data, and choose the best tool for that specific job. 

> A programmer who only knows one path is a passenger; a programmer who knows all the paths is the navigator.

-- Menu-Driven Programs (Loop + Case)

This is where it becomes powerful.

Program runs:

1. Display menu
2. User selects option
3. CASE executes
4. Loop repeats

This is the foundation of:

* ATM systems
* POS systems
* Game menus

* Why do most systems use menus?
* Why combine loop + case?

- Example

2.	do 
		// Display Menu
		output "Enter Selection" 
		output "Play Game" 
		output "Load Saved Game" 
		output "Settings" 
		output "Exit"

		input strSelection // input the string value 

		case strSelection of 			
			"Play Game": playGame() 		
			"Load Saved Game": loadGame()
			"Settings":  settings()
		endcase
	while strSelection <> "Exit"
